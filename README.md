# 基于“3820”战略工程内容的多智能体系统

## 目标与当前状态

建设一个面向研究者、政策分析者和学习者的“3820知识助手与战略推演平台”。用户通过一个问答入口查询《福州市20年经济社会发展战略设想》的背景、目标、路径、指标、空间布局和实施效果。系统必须给出可追溯的依据；缺少依据时明确说明，不能让模型补造事实或数值。

**当前仓库已有示例代码、统一配置、共享接口草案、离线测试和基础数据；它们仍是项目起点，尚未完成本 README 的全部实施与验收步骤。** 可引用的原始资料、真实模型配置、数据核验、生产防护和在线端到端测试仍待补齐。文末的 Word 和 Markdown 文件只用于追溯，实施时以本 README 的步骤、数据和验收标准为准。

### 业务范围

| 主题 | 系统应掌握和提供的内容 |
| --- | --- |
| 三阶段目标 | 1995 年：主要指标在 1990 年基础上再翻一番，提前实现小康；2000 年：城乡各项人均水平等主要指标达到国内先进城市水平；2010 年：达到或接近亚洲中等发达国家或地区当时的平均发展水平。 |
| 四条实施路径 | 以侨引侨、园区为基、深化改革、拓新改旧。回答时应说明路径与具体空间要素、举措和效果的联系。 |
| 五类知识实体 | 阶段目标、指标体系、空间要素、实施路径、效果评估。保留“调研论证 → 战略形成 → 目标分解 → 路径实施 → 实际成效”的关系。 |
| 四项用户能力 | 有来源的知识问答与规划分析；指标查询和计算；空间要素查询和分析；目标达成率与效果评估。复合问题可以组合这些能力。 |

知识资料至少覆盖 1992 年前后的调研论证、三阶段目标、四条路径、主要空间要素和成效。调研信息包括“万人问卷、千人调研、百人论证”、581 个课题、1600 多名参与调研的干部、2.5 万多条市民意见及 1992 年 11 月战略设想审议通过的时间。每项事实应保存出处，不能只把这些文字写进提示词。

### 第 2 步：准备资料并建立数据溯源

**要做的事**

1. 收集获准引用的原始“3820”资料放入 <code>knowledge/data/</code>。指南中的 <code>3820视频.pptx</code> 是示例输入路径，不是唯一允许的资料；当前提取器只支持 PPT，选用其他格式时须增加对应解析器。本仓库目前没有该示例 PPT，也没有其他已核验的原始资料。资料尚未提供时，可以用本 README 的指标表和带出处的测试片段开发，但知识库覆盖率与正式上线验收保持“未完成”。
2. 为每条文本片段或结构化记录保存 <code>source_file</code>、<code>page_or_slide</code>、<code>section</code>、<code>data_version</code>、<code>verified</code> 和提取时间。指标还须保存指标名、单位、年份、统计口径；空间要素还须保存类型、时期、关联路径和来源。
3. 将原始资料与本 README 的数据逐项对照。相同指标有不同数值时保留两个版本并标记冲突，待人工核验后才能作为确定值使用。跨口径或不可比数据不计算增长率。
4. 对扫描页、图片型图表和复杂图示增加 OCR 或人工录入流程。PowerPoint 文本提取成功不代表图片内容已经进入知识库。

**完成标准：** 任一回答使用的事实或指标都能定位到文件、页/幻灯片或表格；无法定位的记录不能作为已核验依据。

### 第 5 步：构建可追溯知识库

在 <code>knowledge/knowledge_base.py</code> 实现以下连续流程：

1. 读取演示文稿的页/幻灯片文本与表格；其他格式资料通过独立解析器接入，统一输出带来源元数据的文档片段。
2. 按语义和长度切分，保留章节、页码和相邻上下文；空片段不入库。
3. 用配置的向量模型生成向量，检查向量条数与片段条数一致、维度一致，并持久化索引与“向量位置 → 片段元数据”的映射。起步可用 FAISS，后续规模化再替换。
4. 实现 <code>retrieve(query, top_k)</code>：返回片段正文、来源、距离/分数和核验状态。<code>top_k</code> 必须受配置和索引大小约束；用测试问题校准相关性阈值，低相关或空结果返回“知识库暂无充分依据”。
5. 封装统一检索接口，便于以后替换为企业知识检索或其他检索服务。调用方不依赖具体向量库。

**完成标准：** “1995 年翻一番目标”等测试查询命中正确片段和页码；空索引、无命中及低相关场景不会产生虚构引用。

### 第 6 步：接入模型并定义工具协议

在 <code>llm_client.py</code> 统一管理火山方舟豆包的 OpenAI 兼容接口、模型 ID、超时和错误分类。实际模型与向量模型必须先在服务端开通；测试使用可替换的假客户端，不能依赖在线模型才能运行单元测试。

在 <code>tools/tools.py</code> 注册并校验三个基础工具：

| 工具 | 输入 | 输出 |
| --- | --- | --- |
| <code>knowledge_retrieve</code> | <code>query: string</code> | 相关片段列表，含正文和来源。 |
| <code>query_indicator</code> | <code>key: string</code>、可选 <code>years: integer[]</code> | 指标值、单位、口径、来源或明确错误。 |
| <code>query_spatial</code> | <code>keyword: string</code>、可选 <code>stype: string</code> | 空间要素列表及来源或无匹配说明。 |

模型选择工具后，用统一的 <code>call_tool</code> 分发并将结果回填对话。未知工具名和非法参数直接返回可诊断的校验错误，不能静默调用其他工具。

**完成标准：** 三个工具均有 schema 测试和成功/失败调用测试；模型服务不可用时其余纯数据能力仍可独立测试。

### 第 7 步：实现五个智能体

五个角色共享同一知识检索接口，但各自只处理职责内的问题：

1. **主智能体：** 将问题拆成子任务并汇总。每个子任务至少有 <code>type</code> 与 <code>question</code>；类型只允许 <code>planning</code>、<code>indicator</code>、<code>spatial</code>、<code>evaluation</code>。指标任务必须有有效 <code>key</code>，可选 <code>years</code>；空间任务必须有 <code>keyword</code>，可选 <code>stype</code>。对模型输出进行 JSON 解析和 schema 校验，非法输出重试或明确报错。汇总时保留各子任务来源、口径、异常和未完成状态。
2. **规划智能体：** 用知识库片段回答背景、三个阶段、四条路径及实施逻辑。输出背景、阶段目标、路径举措、关键依据、风险和建议；证据不足时说明缺口，不能把推测写成历史事实。
3. **指标智能体：** 只从已核验指标记录查询与计算，返回名称、数值、单位、年份、来源、统计口径和计算公式。未知指标/年份有明确反馈。
4. **空间智能体：** 查询并分析港口、机场、园区、苍霞片区、展会和侨商网络，给出要素清单、所属时期、关联路径和出处。
5. **评估智能体：** 接收目标、实际值、目标方向、年份、口径及规则，先验证可比性再计算，输出基准、目标、实际、达成率、公式和结论。不能只生成一段没有计算依据的文字。

**完成标准：** 每个角色均有独立输入输出契约和测试；主智能体不会把缺失参数悄悄替换为默认指标或默认年份。

### 第 8 步：实现评估规则及基准结果

1995 年“翻一番”只适用于已明确可量化的指标：<code>目标值 = 1990 年基准 × 2</code>；上升型指标且目标值大于零时，<code>达成率 = 1995 年实际值 / 目标值 × 100%</code>，四舍五入到 1 位小数。

| 指标 | 1990 基准 | 翻番目标 | 1995 实际 | 预期达成率 |
| --- | ---: | ---: | ---: | ---: |
| GDP（亿元） | 102.40 | 204.80 | 464.14 | 226.6% |
| 人均 GDP（元） | 1936 | 3872 | 8219 | 212.3% |
| GNP（亿元） | 110.91 | 221.82 | 495.55 | 223.4% |
| 城镇居民人均可支配收入（元） | 1537 | 3074 | 4896 | 159.3% |
| 农村居民人均纯收入（元） | 864 | 1728 | 2303 | 133.3% |
| 工业总产值（亿元） | 137.28 | 274.56 | 506.82 | 184.6% |

下降型指标要先确认目标是否为上限；若实际值不高于上限可判为达标，超出时按事先定义的规则计算，处理实际值为零的情况。区间型与定性目标使用明确的判据。2000 年“国内先进城市水平”和 2010 年“亚洲中等发达国家或地区平均水平”需要外部比较对象、比较年份、指标口径和“达到/接近”的阈值；这些资料未准备好时返回“无法评估”，不能套用 1995 年公式。

**完成标准：** 六项 1995 年结果与上表逐项一致；零值、负值、缺失值、不可比数据和定性目标均有明确处理。

### 第 9 步：编排任务与状态

在 <code>graph.py</code> 建立状态图，状态至少包括原问题、子任务、检索上下文、各角色结果、最终答案、<code>request_id</code> 和 <code>thread_id</code>。处理顺序为“解析与校验 → 按需检索 → 条件路由 → 专业智能体执行 → 汇总”。单类型任务只进入对应角色；多类型任务逐个执行并保留每个子任务的结果和错误。只有实现、测试了并发调度与状态合并后，才能把多类型任务改称并行。

开发时可用内存 Checkpoint；上线必须改用持久化 Checkpoint，并依据实际安装的 LangGraph 版本实现快照定位、恢复和续跑。<code>thread_id</code> 按会话或用户隔离，不能让所有请求共用一个默认线程。

**完成标准：** 单类型和混合问题路由正确；单个子任务失败后仍可返回已完成结果；进程重启后能定位并恢复测试会话状态。

### 第 10 步：提供对外 API

在 <code>app.py</code> 实现 <code>POST /chat</code>。请求和响应至少遵守以下结构；字段类型由 Pydantic 校验，<code>question</code> 不能为空：

~~~json
{
  "question": "2010 年福州 GDP 是多少？1995 年翻番目标完成了吗？",
  "thread_id": "session-001"
}
~~~

  "request_id": "服务端生成的唯一 ID",
  "status": "ok",
  "answer": "汇总答案，包含数值、计算口径及来源",
  "results": {
    "indicator_1": {"role": "indicator_1", "status": "ok", "data": "...", "sources": [], "error": null},
    "evaluation_2": {"role": "evaluation_2", "status": "ok", "data": "...", "sources": [], "error": null}
  }

上例只展示结构；<code>sources=[]</code> 表示尚未提供可追溯依据，不能把回答称作已核验。完整来源对象和有效示例见 <code>tests/fixtures/contracts.json</code>。

错误响应包含 <code>request_id</code> 和可理解的错误码/说明，不暴露密钥、内部堆栈或原始服务异常。接口需要认证、授权、限流和请求大小限制；不能把没有这些保护的示例服务直接暴露到公网。若以后增加写操作，为写请求增加幂等键、先查后写和补偿日志。

**完成标准：** 有效、空白、超长和非法请求均有确定响应；每次请求可通过 <code>request_id</code> 查到处理链，用户会话互不串扰。

### 第 11 步：实现故障处理、日志和监控

- 模型超时、HTTP 429 与 5xx、临时断连可用指数退避重试，最多 3 次；认证失败、参数错误和数据缺失不盲目重试。模型仍不可用时调用已配置的备用模型或给出明确降级提示。
- 检索失败最多重试 1 次。无证据时标明“未引用知识库”或“知识库暂无充分依据”，不继续生成缺少依据的事实性结论。
- 编排节点异常时记录快照和已完成结果；恢复必须基于持久化 Checkpoint，不把“找到历史快照”当成“已自动回滚”。
- 结构化日志贯穿 <code>request_id</code>、<code>thread_id</code>、角色、节点、耗时和错误类型；不记录 API 密钥及不必要的敏感内容。
- 监控 QPS、并发、P95 延迟、超时率、错误率、检索无命中率和低相关率。上线前先设定目标阈值，再压测验证。

**完成标准：** 可通过故障注入分别复现并验证模型重试、检索降级、节点失败、重启恢复和完整日志链路。

### 第 12 步：测试、部署和上线验收

1. **单元测试：** 覆盖 13×4 指标完整性、查询与增长率边界值、六项达成率、下降型与定性目标、知识切片和检索阈值、工具参数校验。
2. **集成测试：** 覆盖单类型问题、混合问题、未知指标/年份、空知识库、低相关片段、模型超时、检索失败、部分子任务失败、重复请求和进程重启。
3. **质量检查：** 用事先准备的问题集记录期望答案、实际答案和引用；逐条核对来源。没有依据的答案必须明确拒绝下结论。
4. **部署准备：** 使用验证过的 Python 依赖和镜像；注入真实密钥，配置持久化索引、Checkpoint、访问控制和日志存储；执行重启恢复与压力测试。
5. **上线判定：** 原始资料已补齐且其内容可检索；13×4 数据与原始附件逐项核验；1995 年六项结果一致；故障演练通过；按请求 ID 可追踪；认证、授权、限流和内容安全生效；实测并记录目标并发、压测时长、P95 延迟及错误率。任一项未通过则不标记为生产可用。

## 本地开发与交付物

从项目根目录执行。先确认 `python` 指向 Python 3.11；如果通过 Conda 安装，先激活对应环境。

~~~bash
python --version             # 应显示 Python 3.11.x
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.lock
python -m pytest -m offline -q
cp -n .env.example .env       # 需要调用在线模型时再填写本地配置
# 填好实际密钥、模型 ID 后才能启动在线服务：
uvicorn app:app --host 127.0.0.1 --port 8000
~~~

若本机没有 Python 3.11，可先通过 Conda 执行 `conda create -n 3820_agent_py311 python=3.11 pip` 和 `conda activate 3820_agent_py311`，再运行上面的命令。现有测试可离线执行；启动问答服务仍需完成模型配置和知识资料准备。

更新依赖时，在干净的 Python 3.11 环境中安装 `requirements.txt`，运行 `python -m pip check`，再用 `python -m pip freeze --local > requirements.lock` 重新锁定；随后在另一个空白环境中安装锁定文件并运行 `pytest -q`。不要从装有其他项目包的环境直接生成锁定文件。当前锁定文件在 Linux/WSL 的 Python 3.11 环境中验证。

交付时应包含：可运行代码、锁定依赖、环境变量样例、指标与空间要素数据及来源元数据、知识库构建方式、自动化测试和结果、API 示例、部署配置、故障演练记录与上线检查结果。不要将 <code>.env</code>、真实密钥、个人资料或运行生成的索引直接放入版本库。
